# Cost-Aware Credit Card Fraud Detection

An end-to-end fraud detection pipeline built around a simple idea: catching fraud isn't the same as minimizing business cost. This project goes beyond standard ML metrics (PR-AUC, F1) to select a model and decision threshold based on **expected dollar cost**, and translates results into terms a fraud operations team could actually act on.

## Headline Results

* **Final model:** XGBoost, deployed at a decision threshold of **0.82**
* **Test-set expected cost:** **$3,983.45** (dollar-weighted: missed fraud costed at the transaction's real amount, false positives at a flat $15 investigation cost)
* **Capacity analysis:** reviewing just **0.5% of transactions** (ranked by predicted risk) catches **89.8%** of all fraud in the test set
* **Extrapolated scale:** at this dataset's approximate annual transaction volume (\~52M), the model's estimated residual cost is **\~$3.6M/year** *(illustrative order-of-magnitude estimate, not a forecast — see Limitations)*

## Why This Project Is Different

Most public projects on this dataset stop at "which model has the best PR-AUC." This one asks the questions a bank's fraud operations and risk teams would actually ask:

* **What does a missed fraud or a false alarm actually cost?** Every threshold decision here is grounded in a dollar-weighted cost function, not an abstract metric.
* **How many analysts do we need?** Capacity analysis reframes model performance around review-team staffing constraints, not just a single threshold.
* **Is the model's own validation trustworthy?** Mid-project, cross-validation scores came back suspiciously close to perfect (>0.999 PR-AUC). Rather than accepting a good-looking number, this was investigated and traced to a common, well-documented pitfall: **SMOTE oversampling applied before cross-validation splitting**, which lets synthetic minority-class points leak across CV folds. This is a frequent mistake in public tutorials on this exact dataset — the fix (moving SMOTE inside the CV pipeline via `imblearn.pipeline.Pipeline`) is standard best practice, but catching and correcting it here — rather than reporting an inflated result — reflects the kind of validation discipline real deployment requires.
* **Domain grounding:** built with prior experience in banking operations, informing the cost assumptions, threshold interpretation, and business framing throughout.

## Methodology Summary

1. **EDA** — confirmed extreme class imbalance (0.17% fraud), examined PCA feature distributions, and identified a U-shaped fraud pattern by transaction amount (elevated fraud at very low amounts, consistent with card-testing, and again at high amounts, consistent with cash-out behavior).
2. **Preprocessing** — stratified three-way split (train/validation/test); features scaled on training data only.
3. **Baseline modeling** — Logistic Regression, Random Forest, and XGBoost compared on validation-set PR-AUC.
4. **Hyperparameter tuning** — `RandomizedSearchCV` with SMOTE applied inside the cross-validation pipeline to prevent synthetic-sample leakage across folds.
5. **Threshold tuning \& cost analysis** — a dollar-weighted cost function (real transaction amount for missed fraud, flat investigation cost for false positives) drives threshold and model selection on the validation set; the test set is used exactly once for final reporting.
6. **Interpretability** — SHAP explains global feature importance and individual high-value missed-fraud cases.
7. **Evaluation \& stability** — threshold sensitivity and resampling stability checks at the actual deployed threshold.
8. **Unsupervised comparison** — Isolation Forest evaluated as a label-free alternative, relevant to cold-start fraud scenarios.

## Key Technical Decisions

* **Train / validation / test discipline:** validation is used for every model and threshold decision; the test set is touched exactly once, for final reporting only — protecting against optimistic, decision-influenced results.
* **SMOTE inside the CV pipeline**, not applied upfront — see "Why This Project Is Different" above.
* **Dollar-weighted cost function** instead of an arbitrary unit-cost ratio (e.g. "FN=10, FP=1") — ties model selection directly to a defensible financial framework.
* **PR-AUC over ROC-AUC** as the primary ranking metric, given the severity of class imbalance (ROC-AUC can look strong even when minority-class precision is weak).

## Limitations \& Future Work

* **Anonymized features:** most features (V1–V28) are PCA-transformed and cannot be interpreted in business terms; only `Time` and `Amount` are directly explainable.
* **Small fraud sample:** validation and test sets each contain fewer than 100 fraud cases; individual metrics (e.g., hourly miss rates) can be sensitive to small-sample noise and should be read directionally, not as statistically confirmed patterns.
* **Temporal generalization untested:** the dataset spans only \~48 hours; whether the model holds up as fraud patterns evolve over longer periods is a natural next step, not evaluated here.
* **Segment-specific modeling:** the U-shaped fraud-by-amount pattern suggests separate models per value segment (or value-aware thresholds) could improve performance — identified as future work.
* **Annual cost extrapolation** is an order-of-magnitude illustration based on this dataset's implied scale, not a calibrated forecast for any real institution.
